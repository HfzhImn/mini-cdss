Prasyarat

Pengetahuan Umum Sebelum Memulai

Baca bagian ini sebelum menjalankan command atau mengubah kode.

Apa yang sedang dibangun?

Mini-CDSS adalah Clinical Decision Support System edukasional. Sistem ini membantu pencarian kode WHO ICD-10 dan pemeriksaan pasangan obat berdasarkan data lokal. Sistem ini bukan dokter, bukan alat diagnosis mandiri, dan bukan pengganti pedoman klinis atau validasi tenaga kesehatan.

Alur besarnya adalah: data sumber → preprocessing → vector index → retrieval → prompt grounded → LLM → jawaban dengan sumber. Setiap tahap memiliki tanggung jawab berbeda dan dapat diuji secara terpisah.

Istilah yang wajib dipahami
Istilah Makna sederhana Perannya di proyek
Dataset Kumpulan data sumber yang menjadi rujukan sistem. WHO ICD-10 2019 dan DDInter lokal.
ETL Extract, Transform, Load: membaca, membersihkan, dan menyimpan data. Membuat CSV kanonik dan SQLite.
Embedding Mengubah teks menjadi angka yang mewakili kemiripan makna. Dipakai untuk semantic search.
Vector database Database yang mencari vector paling dekat dengan query. ChromaDB menyimpan index ICD-10 dan DDInter.
BM25 Pencarian berdasarkan kecocokan kata literal. Membantu kode dan nama obat yang harus cocok persis.
RAG Retrieval-Augmented Generation: cari konteks dahulu, baru minta LLM menjawab. Mengurangi jawaban yang tidak bersumber.
API Kontrak komunikasi antaraplikasi melalui HTTP dan JSON. FastAPI menjembatani frontend dengan core RAG.
Hal yang harus dipahami sebelum eksekusi

  2. API key adalah rahasia; simpan di .env, bukan di kode.
  3. Model embedding dan reranker dapat mengunduh ratusan MB.
  4. ChromaDB adalah hasil build; ia bukan pengganti dataset sumber.
  5. Setiap perubahan data atau metadata membutuhkan rebuild index.
  6. Hasil RAG harus dianggap bantuan pencarian, bukan keputusan klinis.
  7. Testing harus dijalankan tanpa API key untuk logic deterministik.

Modul 0

Menyiapkan Laptop Kamu

Sebelum nulis 1 baris kode pun, environment-nya harus benar.

Konsep dulu

Kamu pasti sudah pernah install library Python pakai pip install. Masalahnya: kalau semua proyek Python di laptopmu install library ke tempat yang SAMA (global), proyek A yang butuh versi lama suatu library bisa bentrok dengan proyek B yang butuh versi baru.

Virtual environment (venv) itu solusinya: kotak terisolasi PER PROYEK. Proyek ini punya "kotak" library sendiri, proyek lain punya kotaknya sendiri. Tidak akan saling ganggu.

Praktik

Ekstrak mini-cdss.zip, buka terminal di folder itu, lalu: 

# Cek Python kamu minimal versi 3.11
python --version

# Bikin "kotak" venv bernama "venv"
python -m venv .venv

# Aktifkan kotaknya (WAJIB tiap buka terminal baru untuk kerja di proyek ini)
source .venv/bin/activate        # Mac/Linux
.\.venv\Scripts\Activate.ps1   # Windows PowerShell

# Tanda sudah aktif: nama "(venv)" muncul di depan prompt terminal kamu
⚠ Sebelum install: cek dulu apakah laptopmu punya GPU NVIDIA

sentence-transformers (dipakai untuk embedding di Modul 3) butuh torch. Secara default, pip memasang varian yang sudah termasuk dukungan GPU NVIDIA (CUDA) — ukurannya beberapa GB (banyak paket nvidia-*) karena bundel runtime CUDA-nya sendiri. Ini BENAR & BERGUNA kalau laptopmu memang punya GPU NVIDIA (bisa dicek lewat DirectX Diagnostic Tool / dxdiag di Windows, cari tab Display — kalau ada baris "NVIDIA GeForce ..." di situ, kamu punya). Kalau tidak punya, ukuran itu terbuang percuma.

Pilih salah satu sesuai laptopmu:

Situasi Perintah install
Punya GPU NVIDIA & mau dipakai pip install -e ".[dev]" (default, tidak perlu apa-apa lagi)
Tidak punya GPU, atau mau hemat disk pip install torch --index-url https://download.pytorch.org/whl/cpu dulu, baru pip install -e ".[dev]"

Jujur soal manfaatnya di skala proyek ini SEKARANG (sekitar 10.633 kode WHO dan 130.422 pasangan DDInter pada CSV kanonik untuk di-index): percepatan dari GPU tidak akan dramatis — bukan beda "1 jam jadi 1 menit", lebih ke beberapa detik lebih cepat. Manfaatnya akan lebih terasa kalau nanti dataset diperbesar (upgrade ke WHO ICD-10 penuh, misalnya) atau proyek berkembang ke fine-tuning model beneran (lihat Modul 8). Tapi kalau disk-mu longgar dan GPU-nya sudah ada, tidak ada ruginya dipakai dari sekarang.

Kode-nya sendiri tidak perlu diubah sama sekali untuk pilihan manapun — SentenceTransformer di build_index.py otomatis mendeteksi & pakai GPU kalau tersedia, otomatis fallback ke CPU kalau tidak.

Dependensi rank-bm25, python-multipart, dan sse-starlette sudah terdaftar di pyproject.toml dan requirements.txt. Tidak perlu memasangnya manual. Jika environment sudah pernah dibuat sebelum perubahan ini, ulangi instalasi:

Modul 1

LLM, API, dan Kenapa RAG Dibutuhkan

Konsep inti sebelum menyentuh kode sama sekali.

Konsep dulu

LLM (Large Language Model) seperti Claude/Gemini/Groq itu, secara sederhana, mesin yang sangat pandai menebak "kata apa yang masuk akal berikutnya" berdasarkan miliaran teks yang pernah dilatih. Dia TIDAK punya database fakta yang dia "lookup" — dia menghasilkan jawaban dari pola, bukan dari mencari.

Konsekuensinya: kalau kamu tanya sesuatu yang sangat spesifik (misal "kode ICD-10 untuk penyakit X"), LLM bisa dengan PERCAYA DIRI menjawab kode yang SALAH atau bahkan tidak ada — ini disebut hallucination. Berbahaya banget di domain kesehatan.

RAG (Retrieval-Augmented Generation) adalah solusinya: sebelum LLM menjawab, kita CARI DULU informasi yang relevan dari sumber terpercaya (database kita sendiri), lalu kasih itu ke LLM sebagai "contekan" di prompt, dan perintahkan LLM untuk HANYA menjawab berdasarkan contekan itu — bukan dari ingatannya sendiri. Itu inti dari seluruh proyek ini.

Praktik

Buka src/rag.py, cari variabel SYSTEM_PROMPT. Baca baris "ATURAN WAJIB" di situ — itu literal instruksi tertulis yang memaksa LLM untuk grounding (cuma jawab dari konteks yang diberikan). Ini bukan teori, ini baris kode yang benar-benar dikirim ke LLM tiap kali ada pertanyaan.

Soal API key

Untuk manggil LLM (Groq/Gemini/Claude), kamu butuh API key — semacam password yang membuktikan panggilanmu sah dan dipakai untuk menghitung biaya. JANGAN PERNAH taruh API key langsung di kode atau upload ke GitHub — selalu lewat file .env (lihat .env.example) yang sudah di-ignore git lewat .gitignore.

✓ Checkpoint

Coba jelaskan ke diri sendiri (atau ke teman): kenapa cuma "nanya ke LLM langsung" berbahaya untuk kasus kode ICD-10, dan apa yang RAG lakukan supaya lebih aman? Kalau belum bisa jelasin tanpa buka catatan, baca ulang bagian konsep di atas.

Modul 2

Data: Fondasi dari Segalanya

RAG secanggih apapun percuma kalau datanya jelek.

Konsep dulu

Prinsip "garbage in, garbage out" berlaku keras di sini: RAG cuma bisa menjawab benar kalau data yang di-retrieve memang benar. Makanya sebelum menyentuh AI sama sekali, kita harus tahu PERSIS data kita dari mana, dan seberapa bisa dipercaya.

Proyek ini menggunakan dua dataset kelas medis sungguhan (real-world datasets) untuk memastikan keandalan CDSS kita:

Dataset Sumber Fungsi
ICD-10 WHO 2019 Metadata WHO lokal di ../icd102019enMeta Standardisasi diagnosis dari tiga file hierarki: chapters, groups, dan codes. Pipeline memakai kode terminal (tipe T) sebagai dokumen RAG, bukan ICD-10-CM Amerika.
DDInter CSV lokal di ../ddinter Memberikan pasangan obat dan level interaksi (Major, Moderate, Minor). File yang tersedia tidak memuat mekanisme, sehingga aplikasi tidak mengarang mekanisme tambahan.

Data diproses dalam dua keluaran. Script prepare_*.py membuat CSV kanonik untuk index RAG. Script etl_pipeline.py membuat data/cdss.db untuk inspeksi relasional dan menjaga hubungan chapter-group-code; database SQLite ini belum menjadi sumber langsung retrieval.

Peran & Korelasi Dataset dalam Alur Kerja Klinis

Mengapa kita butuh dua dataset yang berbeda (ICD-10 dan DDInter)? Karena sistem CDSS ini dirancang untuk mendampingi alur kerja dokter secara utuh:

  1. Fase Diagnosis (ICD-10): Bertujuan menjawab "Pasien ini sakit apa secara baku?". Tanpa ICD-10, dokter A mungkin menulis "Sakit Gula" dan dokter B menulis "Kencing Manis". Sistem tidak akan paham bahwa itu penyakit yang sama. Dengan ICD-10, sistem memaksa penggunaan bahasa medis universal (misal kode E11).
  2. Fase Resep (DDInter): Setelah penyakit diketahui, dokter memberikan obat. Di sinilah DDInter mengambil alur, guna menjawab "Apakah kombinasi obat yang diresepkan ini aman?". Sistem ini menjadi safety net (jaring pengaman) untuk menghindari pasien keracunan akibat interaksi dua obat yang saling bertabrakan (Drug-Drug Interaction).

Secara korelasional: ICD-10 bertugas di ranah standarisasi diagnosis, sementara DDInter bertugas di ranah validasi keselamatan pengobatan. Chatbot berbasis RAG yang akan kita bangun akan berfungsi ganda mengakses dua "otak" data ini sesuai konteks pertanyaan klinis dari dokter.

Praktik

Langkah 0 — ETL (Extract, Transform, Load) ke Database. Dataset kita sudah ada secara lokal. Jalankan skrip pemrosesannya untuk mengekstrak teks, membersihkan, dan menyimpannya ke dalam database relasional SQLite (data/cdss.db): 

# Dari root folder mini-cdss
  python -m scripts.prepare_icd10
  python -m scripts.prepare_drug_interactions
  python scripts/etl_pipeline.py

Buka data/cdss.db untuk memeriksa tabel relasional. Untuk RAG, CSV hasil preprocessing tetap harus dibuat sebelum menjalankan python -m src.build_index.

Jumlah baris kedua keluaran memang berbeda. CSV kanonik DDInter yang dipakai untuk embedding berisi sekitar 130.422 pasangan setelah deduplikasi dan validasi severity, sedangkan ETL SQLite memuat sekitar 222.383 baris sumber untuk inspeksi. CSV RAG ICD-10 berisi sekitar 10.633 kode terminal, sedangkan tabel SQLite memuat sekitar 12.221 baris kode dari file codes.

✓ Checkpoint

Buka database cdss.db. Cek tabel icd10_codes dan coba cari kode A00.0 (Cholera). Lihat group_id-nya, lalu telusuri ke tabel icd10_groups untuk melihat kelompok penyakitnya. Bisakah Anda menjelaskan mengapa menyimpan data dalam bentuk relasional bersusun (hirarki) lebih menguntungkan untuk sistem klinis dibanding satu tabel datar?

Modul 3

Mengubah Teks Jadi Angka (Embedding)

Komputer tidak bisa "mengerti" kata — dia cuma bisa hitung angka.

Konsep dulu

Bayangkan tiap kalimat punya "koordinat GPS" di ruang makna — kalimat yang MIRIP MAKNANYA (walau beda kata persis) posisinya BERDEKATAN di ruang itu. "radang usus" dan "gastroenteritis" akan berdekatan walau tidak ada 1 huruf pun yang sama.

Embedding adalah proses mengubah teks jadi "koordinat" itu — dalam praktiknya, sebuah list angka (vector) dengan ratusan dimensi, dihasilkan oleh model AI khusus. Dua teks yang embedding-nya berdekatan (diukur pakai cosine similarity) dianggap mirip maknanya.

Vector database (kita pakai ChromaDB) adalah database yang dioptimalkan untuk menyimpan jutaan koordinat ini dan mencari dengan sangat cepat "koordinat mana yang paling dekat dengan koordinat query saya".

Praktik

Baca docstring di src/build_index.py, lalu jalankan (unduhan model embedding ~470MB, cuma sekali): 

python -m src.build_index

Proses ini membuat embedding untuk CSV kanonik ICD-10 dan DDInter di data/processed/, lalu menyimpannya ke data/chroma_db/. SQLite tidak dibaca oleh indexer saat ini.

✓ Checkpoint

Kalau kamu tanya "apa itu embedding" ke orang lain, bisa jawab tanpa kata "vector" atau "dimensi" (pakai analogi GPS/koordinat makna di atas)? Itu tanda kamu paham konsepnya, bukan cuma istilahnya.

Modul 4

Mencari yang Relevan (Retrieval)

Bagian paling teknis, tapi juga paling berpengaruh ke kualitas jawaban.

Konsep dulu

Ada 2 cara dasar mencari dokumen relevan:

  • Semantic search (pakai embedding Modul 3) — bagus untuk kemiripan MAKNA, tapi kadang kalah presisi untuk istilah/kode yang harus PERSIS sama.
  • BM25 (lexical search) — cara klasik, cocokkan KATA KUNCI literal (mirip cara kerja mesin pencari lama). Lebih tajam untuk istilah eksak, tapi tidak paham sinonim/makna.

Hybrid search = pakai KEDUANYA, lalu gabung hasilnya. Cara gabungnya pakai Reciprocal Rank Fusion (RRF): bukan menjumlah skor mentah (skalanya beda jauh, tidak adil), tapi lihat RANKING (posisi) tiap dokumen di masing-masing metode, lalu dokumen yang rankingnya bagus di KEDUA metode otomatis naik ke atas.

Setelah itu, ada 1 tahap lagi: reranking. Cross-encoder (model AI kedua, lebih lambat tapi lebih teliti) menilai ULANG kandidat yang sudah disaring, karena dia bisa "melihat" query dan dokumen SEKALIGUS (bukan cuma bandingkan 2 koordinat terpisah).

Praktik

Bagian ini bisa dicoba TANPA API key sama sekali karena murni logic, tidak manggil LLM. Coba di Python interaktif: 

python -c "
from src.fusion import tokenize, reciprocal_rank_fusion
print(tokenize('Kolera Tidak Spesifik!'))
# lihat gimana RRF menggabungkan 2 ranking:
print(reciprocal_rank_fusion([[2,0,1], [2,1,0]]))
"

Lalu baca src/retrieval.py — ikuti method search_icd10() dari atas ke bawah, itu urutan: hybrid search → rerank → return top hasil.

✓ Checkpoint

Kalau semantic search SENDIRIAN sudah cukup bagus, kenapa masih perlu BM25? Coba pikirkan 1 contoh query di mana keyword matching (BM25) akan menang dibanding semantic search murni.

Modul 5

Menyambung ke LLM dengan Aman

Sekarang baru manggil LLM sungguhan — setelah semua fondasi di atas siap.

Konsep dulu

Kenapa proyek ini support 3 provider LLM (Groq, Gemini, Claude) bukan cuma 1? Karena masing-masing punya trade-off beda:

Provider Kelebihan
Groq Sangat cepat & murah, cocok untuk query sederhana volume tinggi
Gemini Konteks besar, rate limit gratis tinggi
Claude Kualitas reasoning tinggi untuk kasus kompleks, plus fitur khusus (prompt caching, tool use)

Routing adalah heuristik yang tersedia di src/router.py untuk memilih provider/model berdasarkan kompleksitas pertanyaan. Pada repository saat ini, heuristik tersebut diuji sebagai modul terpisah; CLI dan API masih memakai settings.default_provider. Menghubungkan routing otomatis ke runtime adalah pengembangan lanjutan, bukan perilaku default.

Praktik

Daftar API key gratis di console.groq.com, isi ke file .env (copy dari .env.example dulu). Lalu: 

python -m src.cli
> kode ICD-10 untuk gastroenteritis infeksius pada anak

Perhatikan output di akhir: [model: ... | latency: ...ms | cost: $...] — itu bukti nyata dari Modul 5 (provider apa yang dipakai) DAN pratinjau Modul 6 (metrik yang akan kita ukur formal).

✓ Checkpoint

Coba tanya sesuatu yang SENGAJA di luar dataset kita (mis. "kode ICD-10 untuk patah tulang"). Apakah jawabannya jujur bilang "tidak ditemukan", atau malah mengarang? Kalau jujur, itu bukti sistem grounding-nya (Modul 1) bekerja.

Modul 6

Mengukur: Apakah Ini Beneran Bagus?

"Kelihatannya jalan waktu dicoba manual" bukan bukti yang cukup.

Konsep dulu

Kalau kamu cuma coba 2-3 pertanyaan manual dan "kelihatannya benar", itu TIDAK cukup untuk klaim sistemnya bagus — bisa saja kebetulan pertanyaan yang kamu pilih itu memang mudah. Butuh golden set: kumpulan pertanyaan dengan jawaban benar yang SUDAH kamu ketahui & verifikasi manual duluan (disebut ground truth), baru kita bandingkan jawaban LLM terhadap itu secara sistematis.

4 metrik yang kita ukur:

  • Accuracy — seberapa sering jawabannya benar
  • Hallucination rate — seberapa sering model MENGARANG detail yang tidak ada di data (paling kritis untuk kesehatan)
  • Latency — seberapa cepat
  • Cost — berapa biaya per pertanyaan
Praktik 
python -m src.eval_runner --provider groq --model llama-3.1-8b-instant
      python -m src.compare_results

Baca hasilnya di data/eval/results/*.csv. Lalu buka data/eval/golden_set.py — perhatikan ada 2 "tier": golden_set_curated.py (ditulis tangan) dan bagian generated otomatis di file itu sendiri. Baca docstring-nya untuk paham kenapa dipisah begitu.

✓ Checkpoint

Kalau accuracy 95% tapi hallucination rate JUGA tinggi, apa artinya? (Petunjuk: model bisa saja sering benar KEBETULAN sambil tetap sering mengarang di kasus lain — accuracy tinggi TIDAK otomatis berarti model bisa dipercaya.)

Modul 7

Menulis Kode yang Bisa Dipercaya

Bagian yang paling sering dilewatkan proyek portfolio — dan paling menunjukkan kematangan.

Konsep dulu

3 tool berbeda, 3 jenis masalah berbeda:

Tool Nyari masalah apa
ruff Gaya kode & pola berisiko (linting) — mis. import tidak kepakai, variabel loop salah di-capture
mypy Tipe data yang tidak konsisten (type checking) — sebelum kode dijalankan, bukan pas crash di production
pytest Apakah LOGIC-nya benar (testing) — kamu tulis "harusnya begini", kode dicek otomatis apakah sesuai

Jalankan ketiga tool ini sebagai quality gate lokal. Catatan bug di bawah adalah konteks historis dari proses pengembangan; jangan menganggap semua bug tersebut masih ada di checkout saat ini.

Praktik 
ruff check src/ scripts/ tests/
mypy src/ scripts/ tests/ --ignore-missing-imports
pytest -v

Baca minimal 2 file test di tests/ (mulai dari test_fusion.py, paling pendek) — perhatikan pola assert: tiap test bilang "kalau input begini, output HARUS begitu", persis.

Contoh masalah yang perlu dikenali

Bagian ini membantu membaca hasil lint dan type checking secara kritis. Periksa kembali source saat ini sebelum menyimpulkan bahwa contoh historis berikut masih berlaku.

Contoh aturan ruff B023

Closure lambda menangkap variabel loop

Ini adalah pola umum yang perlu dicari: lambda di dalam loop dapat menangkap variabel secara reference, bukan nilai saat iterasi dibuat. Jika ruff melaporkan B023, gunakan default argument atau fungsi biasa untuk mengikat nilai dengan jelas.

Jangan menyimpulkan pipeline aman hanya karena satu output terlihat benar; tambahkan regression test untuk perilaku yang diharapkan.

Masalah import yang umum

sys.path dan working directory

Import dapat gagal jika command dijalankan dari folder yang salah atau package belum di-install editable. Jalankan command dari root mini-cdss/ dan gunakan pip install -e ".[dev]".

Ini alasan command setup dan test perlu benar-benar dijalankan di environment proyek, bukan hanya dibaca.

Kompatibilitas SDK

Parameter API berubah antarversi

SDK provider dapat mengubah signature dan parameter. Kode saat ini sengaja tidak mengirim temperature ke Anthropic; jika dependency di-upgrade, baca changelog dan jalankan type check serta test adapter sebelum memakai provider tersebut.

Jangan menjadikan komentar lama sebagai bukti kompatibilitas; source, versi dependency, dan test adalah sumber kebenaran.

✓ Checkpoint

Coba SENGAJA rusak sesuatu kecil (misal ubah 1 angka di src/router.py) lalu jalankan pytest lagi. Lihat sendiri test yang gagal dan pesan errornya — ini cara paling cepat merasakan GUNANYA test, bukan cuma baca teori.

Modul 8

Ringkasan: Dari CLI ke Arsitektur Full-Stack

Sebelum lanjut ke API dan frontend, pastikan gambaran besarnya sudah jelas.

Arsitektur yang akan kita bangun

Sampai Modul 7, semua interaksi terjadi lewat CLI. Mulai Modul 9, kita akan membungkusnya menjadi sistem 3 lapis yang bisa diakses dari browser:

Lapisan Teknologi Tanggung jawab
Backend (API) Python · FastAPI Menerima request HTTP, jalankan pipeline RAG, kembalikan JSON
AI Core Python · src/ Retrieval, reranking, LLM call — kode yang sudah ada, tidak perlu diubah
Frontend (UI) TypeScript · Next.js Tampilkan antarmuka chat, kirim request ke backend, render jawaban

Yang penting dipahami: core RAG di src/ sudah tersedia sehingga backend FastAPI dapat memakainya kembali. Endpoint memanggil fungsi yang sudah ada (answer_icd10_query, answer_drug_interaction_query) melalui answer_query(); perubahan pada core tetap harus diuji seperti biasa.

Kenapa FastAPI, bukan Flask atau Django?

Tiga alasan konkret untuk proyek AI seperti ini:

  • Async-native — FastAPI dibangun di atas ASGI, artinya bisa menangani banyak request bersamaan tanpa satu LLM call memblokir yang lain.
  • Pydantic built-in — Validasi request/response JSON otomatis, sama persis dengan yang sudah dipakai di settings.py.
  • Swagger UI otomatis — Dokumentasi interaktif langsung tersedia di /docs tanpa menulis apapun — berguna untuk debugging sebelum frontend jadi.
⚠ Satu hal kritis sebelum Modul 9

Kode LLM client kita (llm_clients.py) adalah synchronous — artinya saat LLM sedang berpikir (bisa 3–10 detik), Python thread itu tidak bisa melakukan hal lain. Di FastAPI, ini berpotensi memblokir seluruh server. Solusinya akan dijelaskan di Modul 9 — tapi penting kamu paham MASALAHNYA dulu sebelum lihat solusinya.

✓ Checkpoint sebelum lanjut

Pastikan semua modul sebelumnya sudah selesai: CLI bisa menjawab pertanyaan, eval runner bisa jalan, dan pytest tidak ada yang gagal. Modul 9 dan 10 membangun DI ATAS fondasi yang sudah ada — kalau fondasinya goyah, bagian baru akan lebih sulit di-debug.

Modul 9

Membangun FastAPI Backend

Membungkus pipeline RAG menjadi HTTP API yang bisa dipanggil dari mana saja.

Konsep dulu: Lifespan dan Singleton

Ingat waktu cli.py dijalankan, dia load model embedding + ChromaDB + reranker duluan, baru baru bisa terima pertanyaan? Proses itu makan waktu ~10–30 detik. Di API server, kita TIDAK bisa melakukan itu setiap ada request — terlalu lambat.

Solusinya: lifespan. FastAPI punya mekanisme untuk menjalankan kode SEKALI saat server start, menyimpan hasilnya di app.state, lalu semua request bisa pakai objek yang sama itu. Ini prinsip singleton: satu instance yang di-share.

Untuk mengatasi masalah LLM sync (lihat Modul 8), kita pakai asyncio.to_thread() — cara Python untuk menjalankan fungsi synchronous di thread terpisah, supaya event loop FastAPI tetap bebas melayani request lain selama LLM sedang berpikir.

# api/main.py
"""
Entry point FastAPI.
Jalankan dengan: uvicorn api.main:app --reload --port 8000
"""
from contextlib import asynccontextmanager

import chromadb
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware
from sentence_transformers import SentenceTransformer

from src.llm_clients import get_client
from src.retrieval import Retriever
from src.settings import settings

from api.routes import query


@asynccontextmanager
async def lifespan(app: FastAPI):
    """
    Kode di dalam 'async with' ini dijalankan SEKALI saat server start.
    Objek berat (embedder, ChromaDB, reranker, LLM client) di-load di sini
    dan disimpan di app.state — di-share ke semua request, tidak di-load ulang.
    """
    if not settings.chroma_db_dir.exists():
        raise RuntimeError(
            f"Chroma index belum tersedia di {settings.chroma_db_dir}. "
            "Jalankan 'python -m src.build_index' terlebih dahulu."
        )
    embedder = SentenceTransformer(settings.embedding_model)
    chroma = chromadb.PersistentClient(path=str(settings.chroma_db_dir))

    app.state.retriever = Retriever(chroma, embedder)
    app.state.llm = get_client(settings.default_provider)
    yield


app = FastAPI(
    title="Mini-CDSS API",
    description="API untuk asisten klinis pencarian kode ICD-10 dan interaksi obat",
    version="1.0.0",
    lifespan=lifespan,
)

# CORS dikonfigurasi di sini — wajib ada agar Next.js (port 3000)
# bisa memanggil API ini (port 8000). Lihat penjelasan lengkap di Modul 11.
app.add_middleware(
    CORSMiddleware,
  allow_origins=settings.allowed_origins,  # default: http://localhost:3000
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)

app.include_router(query.router)


@app.get("/health")
def health_check():
    return {"status": "ok", "message": "Mini-CDSS API is running"}

# api/routes/query.py
import asyncio
from typing import Literal

from fastapi import APIRouter, HTTPException, Request
from pydantic import BaseModel, ConfigDict, Field

from src.rag import RAGResult, answer_query

router = APIRouter(prefix="/api/v1")


class QueryRequest(BaseModel):
    model_config = ConfigDict(str_strip_whitespace=True)
    query: str = Field(..., min_length=3, max_length=500)
    mode: Literal["icd10", "drug", "auto"] = "auto"
    chapter_id: str | None = Field(default=None, min_length=1, max_length=10)
    group_id: str | None = Field(default=None, min_length=1, max_length=10)


class QueryMetadata(BaseModel):
    model: str
    provider: str
    latency_ms: float
    cost_usd: float
    input_tokens: int
    output_tokens: int
    retrieval_count: int


class QueryResponse(BaseModel):
    answer: str
    sources: list[dict[str, object]]
    metadata: QueryMetadata


@router.post("/query", response_model=QueryResponse)
async def handle_query(req: QueryRequest, request: Request):
    """
    Endpoint utama: terima pertanyaan klinis, kembalikan jawaban RAG.

    Catatan asyncio.to_thread(): fungsi answer_*_query() di rag.py adalah
    synchronous (LLM call blocking). Kita jalankan di thread pool terpisah
    supaya event loop FastAPI tidak terblokir saat LLM sedang berpikir.
    """
    if req.mode == "drug" and (req.chapter_id or req.group_id):
        raise HTTPException(
            status_code=422,
            detail="chapter_id dan group_id hanya berlaku untuk mode icd10",
        )

    retriever = request.app.state.retriever
    llm = request.app.state.llm

    try:
        result: RAGResult = await asyncio.to_thread(
            answer_query,
            retriever,
            llm,
            req.query.strip(),
            req.mode,
            req.chapter_id,
            req.group_id,
        )
    except Exception as exc:
        # Log detail di server, tetapi jangan bocorkan detail internal ke client.
        raise HTTPException(status_code=502, detail="Layanan RAG gagal memproses permintaan") from exc

    return result.to_api_dict()

Praktik — Langkah 3: Buat fungsi pemanggil API

Buat file frontend/lib/api.ts:

// frontend/lib/api.ts
import { QueryMode, QueryResponse } from "./types";

const API_BASE = process.env.NEXT_PUBLIC_API_URL ?? "http://localhost:8000";

export async function askQuery(
  query: string,
  mode: QueryMode,
  filters?: { chapter_id?: string; group_id?: string }
): Promise<QueryResponse> {
  const res = await fetch(`${API_BASE}/api/v1/query`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ query, mode, ...filters }),
  });

  if (!res.ok) {
    const error = await res.json().catch(() => ({}));
    throw new Error(error.detail ?? `HTTP ${res.status}`);
  }

  return res.json() as Promise<QueryResponse>;
}

// frontend/app/page.tsx
"use client";

import { useState } from "react";
import { askQuery } from "@/lib/api";
import { QueryMode, QueryResponse } from "@/lib/types";

export default function Home() {

  const [mode, setMode] = useState<QueryMode>("icd10");

      setLoading(false);

            >
              ICD-10
            </button>
            <button
              type="button"
              onClick={() => setMode("drug")}
              className={`px-3 py-1 text-sm rounded border transition-colors ${
                mode === "drug"
                  ? "bg-teal-700 text-white border-teal-700"
                  : "bg-white text-gray-600 border-gray-300 hover:border-teal-500"
              }`}
            >
              Interaksi Obat
            </button>
          </div>

          <div className="flex gap-2">
            <input
              type="text"
              value={query}
              onChange={(e) => setQuery(e.target.value)}
              placeholder={
                mode === "icd10"
                  ? "Contoh: kode ICD-10 untuk gastroenteritis akut"
                  : "Contoh: interaksi warfarin dengan ibuprofen"
              }
              className="flex-1 px-3 py-2 border border-gray-300 rounded text-sm focus:outline-none focus:border-teal-500"

          </div>

        {/* Hasil */}

Modul 11

CORS, Integrasi, & Uji End-to-End

Memastikan frontend dan backend bisa bicara satu sama lain — dan membuktikannya.

Konsep dulu: Apa itu CORS?

Browser punya aturan keamanan: JavaScript di halaman localhost:3000 (Next.js) dilarang memanggil API di domain berbeda (localhost:8000) kecuali server API itu SECARA EKSPLISIT mengizinkan. Aturan ini disebut CORS (Cross-Origin Resource Sharing).

Tanpa konfigurasi CORS yang benar, browser akan memblokir semua request dari Next.js ke FastAPI dengan error Access-Control-Allow-Origin — walau keduanya jalan di laptop yang sama. Kita sudah menambahkan middleware CORS di api/main.py (Modul 9), tapi penting kamu paham KENAPA itu diperlukan.

Situasi Status CORS Yang perlu dilakukan
Development lokal Allow localhost:3000 Sudah dikonfigurasi di main.py
Deploy ke production Allow domain asli Ganti allow_origins ke URL Next.js yang di-deploy
Environment variable untuk URL API

Di frontend/lib/api.ts, kita pakai process.env.NEXT_PUBLIC_API_URL untuk URL backend. Ini penting: saat development, default ke localhost:8000, tapi saat deploy ke production, bisa diganti tanpa ubah kode.

Buat file frontend/.env.local (sudah di-ignore oleh .gitignore Next.js): 

# frontend/.env.local
NEXT_PUBLIC_API_URL=http://localhost:8000

Saat deploy ke production (misal Vercel), isi variabel ini dengan URL server FastAPI kamu di Render/Railway.

audit_report.md Laporan audit sistem mandiri (rekomendasi dan tinjauan teknis per September 2026; laporan historis) terkait kesiapan migrasi backend dari CLI murni menuju arsitektur FastAPI.
README.md & PANDUAN.html Dokumentasi instruksional proyek. Panduan ini adalah kurikulum langkah-demi-langkah (yang sedang Anda baca ini).

Folder api/ (Lapisan Backend FastAPI)

File Fungsi / Penjelasan Inti
api/main.py Pintu masuk utama (entry point) aplikasi FastAPI. Menjalankan konfigurasi lifespan (memuat objek berat ke RAM seperti SentenceTransformer & LLM Client hanya 1 kali saat server nyala), mengatur middleware CORS, dan mendaftarkan router RAG.
api/routes/query.py Endpoint RAG. Menangani request rute POST /api/v1/query dari frontend. Ini menjembatani format web JSON dengan logika RAG di src/rag.py. Sangat esensial karena menggunakan asyncio.to_thread agar LLM tidak memblokir server.

Folder src/ (Lapisan Inti Logika AI & RAG)

File Fungsi / Penjelasan Inti
src/settings.py Pusat manajemen konfigurasi. Membaca .env dengan aman dan mendefinisikan seluruh path/lokasi folder (seperti alamat database dan file CSV) secara dinamis menggunakan modul pathlib.
src/logging_config.py Mengatur format pencatatan log (logging) ke terminal agar informatif dan seragam (menampilkan tanggal, nama modul, dan tingkat urgensi INFO/WARNING/ERROR).
src/llm_clients.py Adapter Provider LLM. Mengandung kerangka dasar LLMClient dan implementasi spesifik ke API asli (GroqClient, GeminiClient, ClaudeClient). Di sini seluruh variasi *provider* diseragamkan input dan outputnya.
src/retry.py Logika Circuit Breaker (decorator @with_retry). Bertugas mengulang panggilan API secara otomatis jika terjadi limit sesaat (rate limit/429) dan menangkap kegagalan koneksi sebelum aplikasi *crash*.
src/build_index.py Sistem ingestion. Skrip khusus pembaca data CSV yang kemudian menjalankan model *embedding* untuk mengubah semua teksnya ke bentuk angka, lalu menanamkannya (indexing) ke database vektor ChromaDB.
src/retrieval.py Mesin Pencari Vektor. Kelas Retriever yang bertugas mencari dan mengambil kumpulan dokumen paling relevan (kandidat ICD-10 atau obat) secara semantik berdasarkan makna query pengguna.
src/fusion.py Menerapkan Reciprocal Rank Fusion (RRF). Ini adalah otak untuk logika hibrida, menggabungkan pencarian vektor (makna) dengan pencarian kata kunci/BM25 (akurasi alfabet).
src/rag.py Sang Dirigen (Orchestrator). Menyatukan hasil pencarian dokumen dari retrieval.py ke dalam satu *prompt* terstruktur, lalu mengirimkannya ke llm_clients.py dengan instruksi Grounding yang ketat agar tidak berhalusinasi.
src/router.py Logika lawas CLI yang mendeteksi arah pertanyaan (ICD-10 vs Obat). Saat ini fungsionalitasnya juga sudah dibalut ke answer_query() di rag.py untuk konsumsi FastAPI.
src/cli.py Antarmuka berbasis terminal lawas yang digunakan untuk eksplorasi dan percobaan lokal (Modul 1-8).
src/eval_runner.py & compare_results.py Skrip penguji otomatis yang membombardir LLM dengan puluhan soal ujian (Golden Set) untuk mengukur tingkat akurasi nyata (Modul 6).

Folder scripts/ (Data Engineering & Eksperimen Tambahan)

File Fungsi / Penjelasan Inti
scripts/prepare_icd10.py & prepare_drug_interactions.py Skrip ETL (Extract, Transform, Load) awal yang menyeleksi dan membersihkan file data mentah berantakan menjadi format CSV rapi di data/processed/.
scripts/demo_*.py Skrip mini independen untuk menguji fitur terisolasi dari model Anthropic (seperti penggunaan *tools* dan caching *prompt*).

Folder tests/ (Quality Assurance & Unit Testing)

File Fungsi / Penjelasan Inti
tests/test_*.py Serangkaian uji kelayakan kode (menggunakan framework pytest). Memastikan logika seperti penggabungan RRF, rute LLM, dan format kualitas CSV berjalan sempurna sesuai hukum deterministik.
💡 Tips Menggunakan Peta Ini

Jika kamu menemui error di Terminal saat Next.js meminta jawaban RAG (contoh: jawaban mengarang tidak beraturan), buka rute perbaikannya: frontend (UI) → api/routes/query.py (Endpoint) → src/rag.py (Prompt Inti) → src/llm_clients.py (LLM Error). Gunakan struktur ini untuk mengisolasi setiap bug!

Modul 13

Filter Chapter & Group ICD-10

Membatasi pencarian sebelum semantic search, BM25, dan reranking berjalan.

Konsep dulu

File icd102019syst_chapters.txt berisi bab besar, file icd102019syst_groups.txt berisi kelompok penyakit, dan icd102019syst_codes.txt berisi kode diagnosis. Setiap kode terminal memiliki chapter_id dan group_id.

Filter harus diterapkan sebelum hybrid retrieval. Dengan begitu, dokumen dari kategori lain tidak ikut masuk ke BM25, semantic search, reranker, atau prompt LLM. Ini lebih presisi daripada mengambil hasil global lalu membuangnya setelah ranking.

Prasyarat penting

Perubahan metadata tidak otomatis mengubah index ChromaDB lama. Setelah preprocessing selesai, wajib rebuild index. Kalau tidak, API akan membaca collection lama yang belum memiliki chapter_id dan group_id.

Langkah 1: Bangun ulang CSV dengan metadata hierarki 
# Jalankan dari root mini-cdss/
python -m scripts.prepare_icd10

# Pastikan kolom baru tersedia
python -c "import pandas as pd; print(pd.read_csv('data/processed/icd10_subset.csv').columns.tolist())"

Output wajib memiliki kolom icd10_code, description, chapter_id, dan group_id. Contoh record: kode A00.0 memiliki chapter 01 dan group A00.

Langkah 2: Simpan metadata ke ChromaDB

Di src/build_index.py, metadata setiap dokumen harus menyertakan identifier hierarki: 

metadatas=[
    {
        "icd10_code": row.icd10_code,
        "description": row.description,
        "chapter_id": row.chapter_id,
        "group_id": row.group_id,
    }
    for row in df.itertuples()
]

Rebuild collection setelah perubahan:

python -m src.build_index
Langkah 3: Terapkan filter di retrieval

Retriever.search_icd10() menerima filter opsional. Jika hanya chapter_id diberikan, pencarian dibatasi ke bab itu. Jika chapter dan group diberikan sekaligus, keduanya harus cocok. 

docs = retriever.search_icd10(
    "pneumonia bakterial",
    chapter_id="10",
    group_id="J15",
)

Filter semantic dikirim ke ChromaDB dengan where, sedangkan BM25 memakai posisi dokumen yang sama sebagai allow-list. Karena kedua ranking memakai kumpulan kandidat yang sama, RRF dan reranking tetap konsisten.

Langkah 4: Gunakan filter melalui API

Field filter bersifat opsional. Tanpa filter, perilaku API tetap seperti sebelumnya. Dengan filter, mode yang sesuai adalah icd10 atau auto. 

curl -X POST http://localhost:8000/api/v1/query \
  -H "Content-Type: application/json" \
  -d '{
    "query": "pneumonia bakterial",
    "mode": "icd10",
    "chapter_id": "10",
    "group_id": "J15"
  }'

Untuk mencari seluruh chapter tanpa membatasi group, hilangkan group_id. Untuk pencarian lama tanpa filter, jangan kirim kedua field tersebut atau isi dengan null.

Langkah 5: Siapkan frontend masa depan

Frontend dapat mengambil daftar chapter dan group dari endpoint metadata yang akan ditambahkan kemudian, atau dari file konfigurasi yang dibangun saat deployment. Bentuk state minimalnya: 

const [chapterId, setChapterId] = useState<string | null>(null);
const [groupId, setGroupId] = useState<string | null>(null);

await askQuery(query, "icd10", {
  chapter_id: chapterId ?? undefined,
  group_id: groupId ?? undefined,
});

Dropdown group sebaiknya di-reset setiap chapter berubah, karena group dari chapter sebelumnya tidak selalu valid pada chapter baru.

Langkah 6: Uji filter 
# Rebuild data dan index terlebih dahulu
python -m scripts.prepare_icd10
python -m src.build_index

# Jalankan unit test
pytest -q tests/test_fusion.py tests/test_data_quality.py

Test yang tersedia memastikan metadata chapter/group tidak kosong, tetapi belum merupakan integration test ChromaDB atau API. Untuk verifikasi filter end-to-end, jalankan server dengan index yang sudah dibangun, kirim request terfilter, lalu pastikan setiap item sources memiliki metadata yang cocok. Test integration otomatis untuk ChromaDB/API masih merupakan pekerjaan lanjutan.

✓ Checkpoint

Kirim dua request dengan query yang sama: satu tanpa filter dan satu dengan chapter_id/group_id. Periksa semua item di sources. Setiap source pada request terfilter wajib memiliki metadata yang cocok dengan filter. Jika tidak, index belum dibangun ulang atau filter belum diteruskan sampai retrieval.
